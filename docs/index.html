Section 1

Executive Summary

This document is a companion technical proposal to the Proposal for Consultancy Services — Senior Web Frontend Developer Consultant (TCIS). It details the end-to-end security architecture implemented for the AfDB enterprise portal: MFA-protected authentication flows, SSO-IDP federation with Google Workspace and Azure AD, OWASP Top 10 hardened frontend middleware, and a fully documented API layer — demonstrating the secure, production-ready web applications that the consultancy engagement will deliver.

The AfDB Secure Enterprise Portal is a modern, security-first web application designed to manage project data, reporting, and operational workflows for the African Development Bank. This proposal details the implementation of three critical security pillars that protect the platform and its users — demonstrating a fully functional proof-of-concept with verified results.

MFA-Protected Access

Multi-factor authentication with TOTP authenticator apps and backup recovery codes

Implemented & Verified

SSO-IDP Federation

Single Sign-On via OAuth2/OIDC with Google Workspace and Microsoft Azure AD

Implemented & Verified

OWASP Top 10 Compliant

Industry-standard security hardening against the most critical web application threats

Implemented & Verified

The system is built as a microservices architecture with a dedicated Authentication Gateway (Beta Backend) that handles all security concerns, and a Data Service (Core Backend) that serves business logic. Both frontends authenticate exclusively through the hardened gateway.

Key Outcomes
  • Zero-trust authentication model with layered security
  • Protection against all OWASP Top 10 vulnerability categories
  • Enterprise SSO federation with Google and Microsoft/Azure AD
  • Account lockout protection against brute-force attacks
  • Input sanitization blocking NoSQL injection and XSS attacks
  • Comprehensive audit logging for all security events

Section 4

Security Implementation: MFA-Protected Access

4.1 Overview

Multi-Factor Authentication (MFA) adds a critical second layer of verification beyond passwords. Users must provide both something they know (password) and something they have (authenticator app or backup code).

4.2 TOTP Implementation

PropertyDetail
AlgorithmTOTP per RFC 6238 via otplib v13
Secret GenerationCryptographically random 32-character base32 secret
QR CodeGenerated as data URL for authenticator app scanning
VerificationTime-windowed token validation with drift tolerance
Issuer Label"AfDB Secure Portal"

4.3 Backup Codes

PropertyDetail
Quantity10 unique codes per user
Format8-character uppercase hexadecimal (e.g., A3F7B2C1)
Storagebcrypt-hashed (10 rounds) — plaintext never stored
UsageOne-time use; marked used: true after verification
RegenerationUsers can generate a fresh set of 10 codes anytime
WarningSystem alerts when 3 or fewer codes remain

4.4 MFA API Endpoints

POST/api/v1/mfa/regenerate-backup-codesYesGenerate new backup code set
GET/api/v1/mfa/statusYesCheck MFA status & remaining codes

Security Implementation: SSO-IDP Federation

5.1 Overview

Single Sign-On (SSO) federation allows users to authenticate through their organization's existing identity provider without managing separate credentials. This implementation follows the OAuth 2.0 Authorization Code Flow.

5.2 Supported Identity Providers

ProviderProtocolAuthorization EndpointUser Info Endpoint
GoogleOAuth 2.0 / OIDCaccounts.google.com/o/oauth2/v2/authgoogleapis.com/oauth2/v2/userinfo
Microsoft / Azure ADOAuth 2.0 / OIDClogin.microsoftonline.com/{tenant}/oauth2/v2.0/authorizegraph.microsoft.com/v1.0/me

5.3 Security Measures

MeasureImplementation
CSRF ProtectionCryptographic state parameter (crypto.randomBytes(32)) validated with timing-safe comparison
Token ExchangeServer-side code exchange (never exposed to client)
State ExpiryStates expire after 10 minutes to prevent replay attacks
Auto-ProvisioningNew SSO users automatically created with viewer role
Account LinkingExisting accounts linked to SSO provider on first login
Provider DiscoveryOnly configured providers appear (no information leakage)

5.4 SSO API Endpoints

MethodEndpointAuthDescription
GET/api/v1/sso/providersNoList available SSO providers
GET/api/v1/sso/initiate/:providerIdNoStart OAuth flow, returns authorization URL
GET/api/v1/sso/callback/:providerIdNoHandle OAuth callback with authorization code

6.2 Security Middleware Stack

The middleware stack is ordered for defense-in-depth. Each layer processes the request before it reaches the route handler:

1
Helmet — Security response headers (CSP, HSTS, X-Frame)
2
Security Headers — Cache prevention, Permissions-Policy, X-XSS-Protection
3
CORS — Origin validation, credential control
4
Body Parser — JSON parsing with 10KB size limit
5
Input Sanitizer — NoSQL injection & XSS pattern detection
6
Morgan Logger — HTTP request logging (combined format)
7
Rate Limiter — 100 req/min general, 5 login attempts/15 min
8
Auth Middleware — JWT validation, user loading, role checking
9
Error Handler — Centralized error handling, no stack trace leakage

Verified HTTP Response Headers

X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Strict-Transport-Security: max-age=31536000; includeSubDomains
Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline'...
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=(), interest-cohort=()
Cache-Control: no-store
X-XSS-Protection: 1; mode=block

9.2 Production Readiness Checklist

  • Set strong JWT_ACCESS_SECRET and JWT_REFRESH_SECRET (min 256-bit)
  • Configure MongoDB with authentication and TLS/SSL
  • Enable Redis persistence and authentication
  • Set NODE_ENV=production
  • Configure TLS/SSL certificates for all endpoints
  • Set up Google and/or Microsoft OAuth2 credentials
  • Configure CORS_ORIGINS with production domains
  • Enable MongoDB audit logging
  • Set up log aggregation (Winston → centralized logging platform)
  • Configure health check monitoring on /health
  • Set up alerting for account lockout events
  • Run security penetration testing before go-live
