Section 1

Executive Summary

This document is a companion technical documentation for the Live Reference Application described in Section 10: Added Value of the Proposal for Consultancy Services — Senior Web Frontend Developer Consultant (TCIS). It details the end-to-end security architecture implemented for the AfDB enterprise portal: MFA-protected authentication flows, SSO-IDP federation with Google Workspace and Azure AD, OWASP Top 10 hardened frontend middleware, and a fully documented API layer — demonstrating the secure, production-ready web applications that the consultancy engagement will deliver.

The AfDB Reference Application is a modern, security-first enterprise web system designed to manage project data, reporting, and operational workflows for the African Development Bank. This live reference application demonstrates in practice the capabilities described in the consultancy proposal — a working, production-deployed system that evaluators can inspect, interact with, and verify.

The system is built as a microservices architecture with a dedicated Authentication Gateway (Beta Backend) that handles all security concerns, and a Data Service (Core Backend) that serves business logic. Both frontends authenticate exclusively through the hardened gateway.

Key Outcomes
  • Zero-trust authentication model with layered security
  • Protection against all OWASP Top 10 vulnerability categories
  • Enterprise SSO federation with Google and Microsoft/Azure AD
  • Account lockout protection against brute-force attacks
  • Input sanitization blocking NoSQL injection and XSS attacks
  • Comprehensive audit logging for all security events

Key Insight

Beta is the gatekeeper — it issues the JWT that Core trusts. Core never handles passwords or MFA; it just validates the token Beta signed. This means authentication logic can be updated, scaled, or replaced independently without touching business logic.

Design Principle

The activity emitter uses a fire-and-forget pattern — Beta sends events to Core via HTTP POST and never blocks on failures. If Core is temporarily unavailable, auth operations continue normally. Events are logged as warnings but never interrupt the user experience. This ensures the monitoring layer adds zero risk to the authentication flow.

Section 5

Email OTP Verification

5.1 Overview

The platform implements email-based One-Time Password (OTP) verification across all authentication flows — login, registration, and password reset. Every user who logs in must verify their identity via a 6-digit code sent to their email address, providing a robust second factor that doesn't require a separate authenticator app.

Login Verification

6-digit code sent after credentials verified — required for every login attempt

Registration Verification

Email ownership confirmed before account creation — prevents fake registrations

Password Reset

Secure code required before password change — protects account recovery flow

5.2 OTP Architecture

PropertyDetail
Code Format6-digit numeric code (100000–999999)
StorageRedis with TTL-based auto-expiry
Expiry600 seconds (10 minutes) — matches countdown timer in UI
Key Pattern{purpose}_otp:{identifier} — e.g., login_otp:userId, register_otp:email, reset_otp:email
DeliverySMTP via Nodemailer with embedded logo (CID attachment)
SecuritySingle-use (deleted from Redis after verification), rate-limited endpoints
Enumeration PreventionPassword reset returns success even for unregistered emails

5.5 Frontend OTP UX

The OTP verification component provides a polished user experience:

  • 6 individual input fields — One per digit, auto-focus advancement
  • Paste support — Users can paste a full 6-digit code (e.g., from email); digits are distributed across fields automatically
  • Countdown timer — 10:00 minute countdown matching the Redis TTL, displayed below the OTP fields
  • Color-coded expiry — Gray (normal) → Orange (≤2 min remaining) → Red (expired)
  • Auto-disable on expiry — Verify button disabled when code expires; message prompts to resend
  • Resend functionality — New code sent, timer resets to 10:00
  • Auto-verify — When all 6 digits are entered, verification is submitted automatically

5.6 Retrieving OTP During Testing (Yopmail)

The demo environment uses Yopmail as the email provider for testing. Yopmail is a disposable email service that allows anyone to view the inbox of any @yopmail.com address without a password.

How to Get the OTP Code
  1. Attempt login at http://localhost:3000/login with credentials (e.g., afdbadmin@yopmail.com)
  2. After credentials are accepted, the UI will show the OTP verification screen
  3. Open a new browser tab and go to https://yopmail.com
  4. Type the email username in the inbox field (e.g., afdbadmin) — no need to type @yopmail.com
  5. Click "Check Inbox" (or the arrow button)
  6. Find the email with subject like "123456 is your AfDB Login Verification Code"
  7. The 6-digit OTP is displayed prominently in the email body — copy or note it
  8. Enter the code in the OTP fields on the login page (or paste all 6 digits at once)
Important Notes
  • OTP expires in 10 minutes — if the timer reaches zero, click "Resend Code" to get a new one
  • Yopmail inboxes are public — anyone can read emails sent to @yopmail.com addresses. Never use for production!
  • Direct inbox link — You can also go directly to https://yopmail.com/en/?afdbadmin (replace afdbadmin with the username)
  • Email may take 10–30 seconds — SMTP delivery is not instant; refresh the Yopmail inbox if the email doesn't appear immediately
